# Как здесь работать

В репозитории работают несколько разработчиков, поэтому конвенции зафиксированы
здесь, а не остаются в голове (тех. ТЗ 9.6). Правила ниже — не пожелания:
нарушение границ доменов и требований из `docs/` считается ошибкой независимо от
того, работает код или нет.

---

## 1. Перед первым изменением кода

Прочитать целиком три файла в [`docs/`](docs/). Это входные требования, а не
справочный материал:

| Файл | О чём |
|---|---|
| [`docs/TZ_navigator_bot.md`](docs/TZ_navigator_bot.md) | продуктовое ТЗ: блоки, кнопки, сценарии |
| [`docs/TZ_tech_stack.md`](docs/TZ_tech_stack.md) | техническое ТЗ: сервисы, модели, эндпоинты, фоновые задачи |
| [`docs/design_from_claude.md`](docs/design_from_claude.md) | дизайн-хендофф: 16 экранов, токены, анимации |

У каждого есть раздел «Уточнения заказчика» в конце — он **перекрывает**
основной текст своего файла. Порядок приоритетов при конфликте и список
неотменяемых инвариантов — в [`CLAUDE.md`](CLAUDE.md).

Исходники дизайна лежат в [`docs/design/`](docs/design/). Тексты 10 вопросов
теста и 15 отписок поддержки переносятся из `docs/design/source/app.jsx`
**дословно** — сочинять заново нельзя.

## 2. Инструменты

| Инструмент | Зачем | Версия |
|---|---|---|
| Docker + Docker Compose | локальный запуск всей системы | compose v2+ |
| [uv](https://docs.astral.sh/uv/) | зависимости и запуск Python-сервисов | 0.8+ |
| [pnpm](https://pnpm.io/) | зависимости фронтенда | 10.33 (пин в `package.json`) |
| Python | Core API, Worker, AI Gateway | 3.13 |
| Node | мини-приложение | 22+ |

```bash
make env       # .env из .env.example
make install   # зависимости всех сервисов
make up        # поднять всё в docker
make check     # линтеры, типы и тесты — то, что должно быть зелёным перед пушем
```

`make` без аргументов покажет остальные команды.

## 3. Структура монорепо

```
apps/
  core/         Core API (FastAPI + Tortoise) и Celery-воркер — один пакет `navigator`
  ai-gateway/   AI Gateway (FastAPI) — пакет `navigator_ai`, независим от `navigator`
  miniapp/      мини-приложение (React + Vite + TypeScript)
infra/
  postgres/     init-скрипты кластера для локального запуска
docs/           требования и дизайн — источник истины
```

**Почему Core API и Worker — один пакет и один образ.** Тех. ТЗ 1.3 требует,
чтобы воркер «не шарил процесс с Core API»: подвисший запрос к сайту вуза не
должен деградировать ответы пользователям. Это выполняется отдельными
процессами в отдельных контейнерах (`core-api`, `worker`, `beat`). Общий пакет
при этом обязателен: задачи работают через сервисный слой доменов, а не через
копию бизнес-логики.

**Почему AI Gateway — отдельный пакет.** Он единственная точка вызова LLM
(тех. ТЗ 1.2) и не должен видеть доменные модели, а домены — провайдеров LLM.
Ценой этого идёт небольшое дублирование инфраструктурного кода (конфигурация,
логи): тянуть ради него общую библиотеку значило бы связать деплой двух
сервисов, от чего разделение и уходило.

## 4. Границы доменов — главное правило бэкенда

Домены живут в `apps/core/src/navigator/domains/<домен>/`:

```
models.py     модели Tortoise — приватны для домена
schemas.py    pydantic-схемы HTTP-слоя
service.py    бизнес-логика; ЕДИНСТВЕННАЯ публичная граница домена
router.py     эндпоинты FastAPI
sources.py    реестры внешних источников домена, если они есть
```

Фоновые задачи домена лежат не здесь, а в `navigator/worker/tasks/<домен>.py`:
задача — такой же внешний потребитель домена, как и HTTP-роут, а расписание Beat
удобнее ревьюить в одном месте.

Состав по тех. ТЗ 3: `users`, `career_test`, `vuz_selection`, `tracker`,
`schedule`, `mentor_qa`, `gamification`, `food`, `support`, плюс `notifications`
из уточнения У25.

**Правило.** Домен не импортирует `models`, `schemas` и `router` другого домена.
Только `navigator.domains.<другой>.service`.

```python
# нельзя
from navigator.domains.users.models import User
from navigator.domains.users import models
from ..users import models

# можно
from navigator.domains.users import service as users_service
from navigator.domains.users.service import get_profile
```

Правило проверяется автоматически: `apps/core/tests/test_domain_boundaries.py`
разбирает AST всех модулей доменов, включая относительные импорты. Тест сам
покрыт тестами на синтетических примерах — зелёный результат на пустом дереве
доменов ничего не доказывал бы.

Зачем это нужно: любой домен можно вынести в отдельный сервис, не переписывая
бизнес-логику (тех. ТЗ 1.1), и правка блока 5 не ломает блок 6.

### Как добавить домен

1. Создать пакет `navigator/domains/<домен>/` с файлами из списка выше.
2. Дописать `"navigator.domains.<домен>.models"` в `DOMAIN_MODEL_MODULES`
   (`navigator/db.py`) — это единственное место регистрации моделей.
3. Создать миграцию aerich (раздел 7).
4. Подключить роут одной строкой `include_router` в `navigator/api/router.py`.
5. Если у домена есть фоновые задачи — модуль в `navigator/worker/tasks/`
   и запись в `BEAT_SCHEDULE` (`navigator/worker/celery_app.py`).

### Вертикальные срезы

Блоки делаются срезами: домен + эндпоинты + экран вместе, а не «сначала весь
бэкенд». Порядок по зависимостям: меню и профиль → блок 1 (тест) → блок 2
(подбор вуза) → блок 3 (трекер) → блок 4 (расписание) → блок 5 (вопросы) →
блок 6 (рейтинг) → блок 7 (еда) → блок 8 (поддержка).

## 5. Внешние источники — только за интерфейсом

Уточнения У3 и У8: каждый внешний источник закрыт интерфейсом минимум с двумя
реализациями — фикстурной и реальной. Выбор делает конфигурация.

**`if DEMO:` внутри доменной логики — ошибка.** Домен получает готовую
реализацию и не знает, откуда пришли данные.

```python
# navigator/domains/food/sources.py
from typing import Protocol

from navigator.sources import SourceRegistry


class FoodSpotSource(Protocol):
    async def nearby(self, latitude: float, longitude: float) -> list[FoodSpot]: ...


food_spots: SourceRegistry[FoodSpotSource] = SourceRegistry("food_spots")


@food_spots.register("fixture")
def _fixture() -> FoodSpotSource:
    return FixtureFoodSpotSource()


@food_spots.register("yandex")
def _yandex() -> FoodSpotSource:
    return YandexMapsFoodSpotSource(api_key=...)
```

Активный режим приходит из настроек полем `source_<имя>`, которое добавляется
в `navigator/config.py` вместе с источником. Неизвестный режим падает на старте
с подсказкой, а не превращается в `None` в глубине домена.

Что реальное с самого начала, а что фикстурное — таблица в уточнении У3:

- реальные: справочник вузов (10–15 настоящих вузов с координатами),
  вакансии hh.ru, точки питания на картах, LLM;
- фикстурные: проходные баллы, бюджетные места, стоимость обучения, общежития,
  даты приёма, конкурсные списки, расписание групп, стартовое наполнение ленты
  вопросов и рейтинга.

Цифры приёмной кампании демонстрационные и помечаются как демо-данные **на
уровне ответа API**, а не только в вёрстке (уточнение У4).

### Уведомления

Фоновая задача никогда не отправляет ничего наружу сама. Уведомление — это
запись в очередь домена `notifications`; доставку выбирает транспорт
`NotificationTransport`: `InAppTransport` по умолчанию (запись в БД и есть
доставка) и `MaxBotTransport`, который включается, когда появятся бот и токен
(уточнение У25). Ни одна задача не знает, какой транспорт активен.

## 6. Конфигурация

Всё окружение читается в одном месте: `navigator/config.py` и
`navigator_ai/config.py`. Имена переменных совпадают с именами полей, список —
в [`.env.example`](.env.example).

**MOCK_AUTH.** Пока нет бота, токена и хостинга, подпись `initData` от MAX не
проверяется, а идентификатор пользователя берётся из заголовка
`X-Max-User-Id` — приложение открывается в обычном браузере (тех. ТЗ 9.3).

- значение по умолчанию в коде — **выключено**;
- `docker-compose.yml` включает его для локального запуска;
- в `ENVIRONMENT=production` сервис с этим флагом **не поднимется** — это
  проверка в валидаторе настроек, а не предупреждение в логе;
- проверка подписи пишется сразу и работает, когда флаг снят.

Весь доступ к платформе MAX (`initData`, нативная кнопка «назад», haptics,
тема) изолируется в один модуль-адаптер. Причина в тех. ТЗ 9.7: точный формат
`initData`, алгоритм проверки подписи и имя npm-пакета SDK лежат в закрытой
документации `dev.max.ru` и первичными источниками пока не подтверждены.
Опираться в коде на догадки об этом нельзя.

## 7. Миграции базы

Миграции — aerich, конфигурация в `apps/core/pyproject.toml`.

Первой миграции пока нет: доменов с моделями ещё нет. Первый домен создаёт её
так:

```bash
cd apps/core
uv run aerich init-db          # только один раз, для первого домена
uv run aerich migrate --name add_users   # для последующих изменений
uv run aerich upgrade
```

До появления первой миграции локальная схема создаётся из моделей флагом
`DB_GENERATE_SCHEMAS=true` (включён в `docker-compose.yml`). Как только
миграции появятся, флаг из compose убирается: в production он запрещён.

## 8. Фронтенд

- **Кнопка «Главное меню» — архитектурно, не вручную.** Она рендерится в общем
  layout-роуте `AppLayout`, который оборачивает все маршруты без исключения
  (ТЗ 1.1, тех. ТЗ 8.3). Новый экран физически не может оказаться без кнопки
  возврата, если он зарегистрирован в дереве роутов.
- **E2E-обход всех роутов не откладывается.** Это единственная автоматическая
  проверка требования №1 продуктового ТЗ, и она остаётся в любом объёме работ
  (тех. ТЗ 9.5). Прогоняется на мобильном и десктопном профиле — ТЗ 0.2.
- **Server state — только TanStack Query. Zustand не хранит копии серверных
  данных** (тех. ТЗ 8.2): ни списка вузов, ни вопросов, ни профиля. Zustand —
  сценарное и UI-состояние.
- **Черновики переживают выход в меню, прогресс теста — намеренно нет.**
  Баллы ЕГЭ, дедлайны, позиция в списке — Zustand с `persist` в
  `sessionStorage`. Прогресс профориентационного теста — обычный локальный
  state без persist: уход с экрана сбрасывает его, это требование ТЗ 1.3, а
  не баг.
- **Хексы не хардкодятся.** Токены Organic живут в теме как CSS-переменные,
  компоненты используют только их (инвариант 7). Палитра фиксированная: тема
  мессенджера MAX не применяется, тёмной версии нет (уточнение Д6).
- **`focus-visible` обязателен** — в прототипе он опущен, в реализации должен
  быть.
- **Пользовательский контент рендерится текстом.** `dangerouslySetInnerHTML`
  запрещён правилом eslint (тех. ТЗ 8.11).
- **Типы API генерируются, а не пишутся руками:** `make api-types` из схемы
  OpenAPI живого Core API (тех. ТЗ 8.6).

## 9. Тесты

Объём осознанно урезан (тех. ТЗ 9.5) — с одним исключением, которое не
урезается.

**Обязательно:**

- e2e-обход всех зарегистрированных роутов с проверкой кнопки «Главное меню»;
- тест границ доменов (`test_domain_boundaries.py`) — зелёный на каждом PR.

**По остаточному принципу:** unit-тесты доменной логики (расчёт шансов,
начисление баллов, веса теста), интеграционные тесты Core API.

**Правила, которые стоит держать:**

- Доменная логика тестируется без БД и без сети: расчёты — чистые функции.
- LLM в тестах — только `mock`-провайдер. Настоящие вызовы недетерминированы,
  медленны и стоят денег (тех. ТЗ 7).
- Интеграционные тесты идут в отдельную базу `<POSTGRES_DB>_test` и в
  отдельный номер базы Redis. Адреса — `TEST_DATABASE_URL` и `TEST_REDIS_URL`,
  по умолчанию localhost. Если сервисы не поднялись, тесты **пропускаются** с
  подсказкой, а не падают: `make test` работает и без docker.
- Тест, который проверяет пустое дерево, не доказывает ничего. Если проверка
  нетривиальная — покрыть саму проверку синтетическими примерами.

## 10. Стиль кода

- **Python:** ruff (линтер и форматтер) + mypy в strict. Строка 100 символов.
- **TypeScript:** eslint с проверкой типов + prettier. Строка 100 символов.
- Комментарии и docstring — по-русски, как и вся документация проекта.
  Комментарий объясняет **почему**, а не пересказывает код.
- Ссылки на требования — по номеру пункта («ТЗ 1.1 закольцованная навигация»,
  «уточнение У19»), а не пересказом.

`make fmt` приводит код в порядок, `make lint` проверяет.

## 11. Ветки и коммиты

- Работа идёт в рабочей ветке, указанной в задаче. В `main` без явного
  разрешения не пушим.
- Pull request открывается только по явной просьбе заказчика.
- Коммиты мелкие и тематические: один коммит — одно осмысленное изменение.
- В сообщении коммита ссылка на пункт требований, если он есть.
