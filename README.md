# Навигатор — мини-приложение для мессенджера MAX

Образовательный сервис для хакатона MAX × Минобрнауки, трек 2 «Образовательные
решения». Мини-приложение открывается внутри мессенджера MAX и закрывает восемь
функциональных блоков плюс профиль пользователя: профориентационный тест, подбор
вуза по баллам ЕГЭ, трекер конкурсных списков, расписание и дедлайны, вопросы
старшекурсникам, рейтинг активности, точки питания рядом с вузом, поддержка.

Требования — в [`docs/`](docs/), они первичны. Что уже сделано и что следующее —
в [`PLAN.md`](PLAN.md). Почему код устроен именно так — в
[`DECISIONS.md`](DECISIONS.md). Конвенции разработки — в
[`CONTRIBUTING.md`](CONTRIBUTING.md). Неотменяемые инварианты продукта — в
[`CLAUDE.md`](CLAUDE.md).

## Запуск

```bash
cp .env.example .env
docker compose up --build        # бэкенд
pnpm install && pnpm --filter miniapp dev   # фронтенд на хосте
```

Или через make:

```bash
make up          # бэкенд в docker
make dev-front   # мини-приложение на http://localhost:5173
```

**Фронтенд по умолчанию в docker не поднимается.** Он объявлен в профиле
`frontend`: dev-сервер Vite в контейнере даёт медленный HMR через смонтированный
том и пересборку образа на каждое изменение зависимостей. Кому удобнее прежний
вариант — `make up-all` или `docker compose --profile frontend up`.

Что поднимется:

| Сервис | Адрес | Что это |
|---|---|---|
| `miniapp` | http://localhost:5173 | мини-приложение, dev-сервер Vite (только с профилем `frontend`) |
| `core-api` | http://localhost:8010/docs | Core API: модульный монолит, FastAPI + Tortoise |
| `admin` | http://localhost:8001 | админка: очереди обращений и спорных вопросов (У26) |
| `worker` | — | Celery-воркер фоновых задач |
| `beat` | — | планировщик Celery Beat |
| `ai-gateway` | только внутри docker-сети | единственная точка вызова LLM |
| `postgres` | localhost:5432 | все бизнес-данные |
| `redis` | localhost:6379 | кэш внешних API и брокер очередей |

Перед стартом приложения отрабатывают два разовых шага: `migrate` приводит
схему базы к моделям, `seed` заливает справочники — вузы, направления, вопросы
теста, программы приёмной кампании и расписания групп. Оба идемпотентны и
выполняются при каждом подъёме; справочники можно залить и отдельно —
`make seed`.

**Админке нужен `ADMIN_PASSWORD`** в `.env`: без него она не поднимается. В её
очередях лежат тексты обращений пользователей, и открытой она быть не может.
Доступ — HTTP Basic, логин по умолчанию `admin` (уточнение У26, тех. ТЗ 9.4).

**Мини-приложение ходит в API через прокси dev-сервера**, а не по адресу
`localhost:8010`: браузеру хватает одного порта 5173, и CORS не нужен. Порт
Core API публикуется только для разработчика — открыть `/docs` и сходить
`curl`. Если он занят, задайте свой в `CORE_API_PORT`; на работу приложения это
не влияет.

AI Gateway наружу не публикуется намеренно: это внутренний сервис (тех. ТЗ 5).
Порты Postgres и Redis открыты только на `127.0.0.1` — для `psql` и `redis-cli`
разработчика.

## Проверки

```bash
make check      # линтеры, типы и все тесты, кроме e2e
make test-e2e   # Playwright на мобильном и десктопном профиле (ТЗ 0.2)
```

Разработка без docker — `make dev-core`, `make dev-front` и остальные цели
`make dev-*`; полный список команд показывает `make`.

## CI/CD

Проверки — [`.github/workflows/ci.yml`](.github/workflows/ci.yml), выкладка —
[`.github/workflows/deploy.yml`](.github/workflows/deploy.yml).

CI гоняется на каждом пуше и в каждом pull request, пятью параллельными
заданиями: бэкенд (линтеры, типы, тесты на настоящих Postgres и Redis, проверка
что миграции не разошлись с моделями), фронтенд, совпадение типов фронта со
схемой бэкенда, e2e на обоих профилях устройств и сборка всех трёх образов.

Деплой подписан на **завершение** CI, а не на пуш: обогнать проверки он не
может. Выкладывается только `main` и только тот коммит, который прошёл CI, —
не «последний в ветке». Образы уезжают в GHCR с тегом коммита, на сервере
`docker compose -f docker-compose.prod.yml pull && up -d`, после чего workflow
дёргает `https://<домен>/health` и падает, если стенд не ответил.

**Сейчас деплой выключен, и это не требует правок кода.** Сервера нет, поэтому
задание `guard` не находит секретов, пишет в отчёт, каких именно, и на этом
останавливается. Чтобы включить, добавьте в Settings → Secrets and variables →
Actions:

| Секрет | Что это |
|---|---|
| `DEPLOY_HOST` | адрес сервера |
| `DEPLOY_USER` | пользователь для SSH |
| `DEPLOY_SSH_KEY` | приватный ключ этого пользователя |
| `DEPLOY_KNOWN_HOSTS` | вывод `ssh-keyscan ваш-хост` — без него ключ сервера не сверяется |
| `DEPLOY_DOMAIN` | домен для проверки стенда после выкладки |

На сервере до первого деплоя нужен Docker с плагином compose, каталог
`/opt/navigator`, принадлежащий пользователю деплоя, и в нём `.env` — по образцу
[`.env.prod.example`](.env.prod.example). Деплой этот файл не трогает: пароли
стенда не должны проходить через git и через логи Actions.

Стенд поднимается с `ENVIRONMENT=staging` и `MOCK_AUTH=true` — пока алгоритм
проверки подписи `initData` не сверен с документацией MAX (тех. ТЗ 9.7). Это
значит, что стенд демонстрационный: любой запрос может назвать себя любым
пользователем, и публичной ссылкой на него делиться не стоит.

## Архитектура

```
┌──────────────────┐      ┌────────────────────┐      ┌─────────────────┐
│  React Mini App  │─────▶│  Core API          │─────▶│  AI Gateway     │
│  MAX Mini Apps   │      │  FastAPI+Tortoise  │      │  YandexGPT /    │
└──────────────────┘      │  PostgreSQL        │      │  GigaChat       │
                          └─────────┬──────────┘      └─────────────────┘
                                    │ ставит задачи
                                    ▼
                          ┌────────────────────┐
                          │  Worker            │
                          │  Celery + Beat     │───▶ внешние API
                          │  Redis (broker)    │     (hh.ru, Карты,
                          └────────────────────┘      сайты вузов)
```

Модульный монолит с двумя вынесенными сервисами. Разделение оправдано
паттернами отказа, а не модностью: LLM-вызовы — самая нестабильная по времени
ответа часть системы, фоновые задачи ходят во внешние источники, которые умеют
подвисать. Подробнее — тех. ТЗ, раздел 1.

Структура каталогов и правила границ доменов — в
[`CONTRIBUTING.md`](CONTRIBUTING.md).

## Состояние работ

Что сделано, что следующее и чем оно заблокировано — в [`PLAN.md`](PLAN.md).
Здесь это специально не дублируется: два места с состоянием расходятся на
первой же неделе, и непонятно, какому верить.

### Что известно про платформу MAX

Официальная документация `dev.max.ru` закрыта сетевой политикой окружения
разработки: egress-прокси отвечает 403 на CONNECT. Поэтому формат `initData`,
алгоритм проверки подписи, API нативной кнопки «назад» и имя npm-пакета SDK
мини-приложений первичными источниками **не подтверждены** — см. тех. ТЗ 9.7.

Разработку это не блокирует: режим `MOCK_AUTH` открывает приложение в обычном
браузере, а весь доступ к платформе изолирован в один модуль-адаптер. Проверка
подписи пишется сразу и включается снятием флага, когда документация станет
доступна.
